# Rewardly V2

## Scalable Telegram Mini App Platform — Complete Technical Architecture & Database Specification

**Version:** 2.0
**Platform:** Telegram Mini App
**Frontend:** Next.js 14+ / React
**Backend:** Node.js / Express.js
**Database:** PostgreSQL
**ORM:** Sequelize
**Cache:** Redis
**Automation:** n8n
**AI:** Optional Agentic AI Layer
**Primary Communication:** Telegram Bot API
**Admin:** Single Supreme Admin
**Architecture:** Modular Monolith + Event-Driven Extensions

---

# 1. Executive Summary

Rewardly V2 is a scalable rewards and engagement platform designed primarily as a Telegram Mini App.

The platform allows users to:

* Earn coins through offers, tasks, games and activities
* Complete offer tiers
* Participate in contests
* Participate in lucky draws
* Claim daily rewards
* Refer other users
* Maintain streaks
* Manage their wallet
* Request withdrawals
* Receive Telegram notifications

The platform also provides a powerful Supreme Admin Panel for:

* User management
* Earning management
* Financial management
* Withdrawal review
* Fraud investigation
* Referral management
* Broadcasts
* Analytics
* System configuration
* Audit logs

The architecture is designed to support future automation through n8n without making n8n responsible for core business logic.

The central principle is:

> **Rewardly must operate normally even when n8n or AI is completely unavailable.**

n8n and AI are extension layers, not dependencies of the core platform.

---

# 2. Core Architecture Principles

Rewardly V2 follows these principles:

### 2.1 PostgreSQL is the source of truth

All important business data lives in PostgreSQL.

Examples:

* Users
* Wallets
* Transactions
* Withdrawals
* Offers
* Referrals
* Contests
* Notifications
* Audit logs

Redis must never become the authoritative source for financial data.

---

### 2.2 Business logic belongs in the backend

Core rules must be implemented inside Express services.

Examples:

* Can the user withdraw?
* How many coins can be deducted?
* Is a referral valid?
* Is an offer completion valid?
* Can a user claim a reward?
* Can a withdrawal be approved?

These must not depend on n8n or an LLM.

---

### 2.3 n8n is an automation layer

n8n handles:

* Scheduled workflows
* Event-triggered workflows
* Notifications
* Analytics automation
* AI workflows
* External integrations

n8n should call controlled backend APIs instead of directly modifying PostgreSQL.

---

### 2.4 AI is optional

The platform should continue functioning if:

* AI API is unavailable
* n8n is unavailable
* an AI workflow fails
* an automation times out

---

### 2.5 Financial operations must be atomic

Wallet and withdrawal operations must use database transactions.

A financial operation should either:

**completely succeed**

or

**completely fail**

Never leave half-completed state.

---

### 2.6 Every important action must be traceable

The platform must answer:

> Who did what, when, to which entity, and why?

This applies to:

* Admin actions
* Wallet changes
* Withdrawals
* Fraud decisions
* Automated actions

---

# 10. Wallet Rules

Every balance-changing operation must:

1. Start a database transaction
2. Lock the relevant wallet row
3. Validate balance
4. Create ledger entry
5. Update wallet balance
6. Create corresponding event
7. Commit

Example:

```text
Withdrawal
    |
    v
BEGIN TRANSACTION
    |
    v
Lock Wallet
    |
    v
Check Balance
    |
    v
Deduct Coins
    |
    v
Create Ledger Record
    |
    v
Create Withdrawal
    |
    v
Create Outbox Event
    |
    v
COMMIT
```

---

# 11. Idempotency

Critical operations must be idempotent.

Examples:

* Withdrawal
* Reward credit
* Offer completion
* Referral reward
* Notification action
* n8n-triggered operations

Create idempotency keys where required.

```text
idempotency_key
----------------------------
UNIQUE
```

If the same request arrives twice:

```text
Request #1 → Process
Request #2 → Return existing result
```

This prevents duplicate rewards and duplicate withdrawals.

# 43. Database Constraints

Use database constraints aggressively.

Examples:

```text
UNIQUE telegram_id

UNIQUE application.slug

UNIQUE user_id + application_id

UNIQUE wallet user_id + currency

UNIQUE lifafa_id + user_id
```

Use foreign keys wherever relationships are required.

Use CHECK constraints where appropriate.

Do not rely solely on application code for data integrity.

# 63. What Should NOT Be Done

## Do not create microservices immediately.

Use a modular monolith first.

## Do not give n8n database credentials.

Use internal APIs.

## Do not give AI unrestricted database access.

Use controlled tools.

## Do not put everything inside users.

Separate domains.

## Do not use Redis as financial truth.

PostgreSQL is authoritative.

## Do not rely only on frontend validation.

Validate on the backend.

## Do not directly edit balances.

Use ledger operations.

## Do not depend on n8n for core application functionality.

The platform must operate independently.

## Do not expose admin secrets in localStorage.

Use secure authentication.

# 67. Final Design Philosophy

Rewardly V2 should be built as a **platform**, not simply as a Telegram Mini App.

The core platform should provide:

```text
IDENTITY
   ↓
USER MANAGEMENT
   ↓
EARNING
   ↓
WALLET
   ↓
TRANSACTIONS
   ↓
WITHDRAWALS
   ↓
REFERRALS
   ↓
FRAUD
   ↓
NOTIFICATIONS
   ↓
ANALYTICS
   ↓
ADMIN
   ↓
EVENTS
   ↓
AUTOMATION
   ↓
AI
```

The most important architectural separation is:

```text
CORE PLATFORM
       |
       +---- User
       +---- Earning
       +---- Wallet
       +---- Finance
       +---- Referral
       +---- Fraud
       +---- Admin
       +---- Analytics
       |
       +---- Event Layer
                    |
                    v
                  n8n
                    |
                    v
             Automation / AI
```

**Core application = reliable and deterministic.**

**n8n = automation.**

**AI = intelligence.**

This gives Rewardly a clean foundation that can support the current Mini App while remaining ready for Stuearn, RewardVerse and future applications without forcing the entire system to be rebuilt.
